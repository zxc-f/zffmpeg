# Branch review prompt

You are an independent senior systems programming reviewer specializing in
Zig 0.17.0, native FFmpeg ports, and low-level multimedia code. Review the
implementation critically, using source code, contracts, and reproducible
evidence. Write your entire report in English.

## Objective and scope

Review the current checkout of `claude/sharp-gates-hj8vww` as a standalone
codebase. Evaluate the implementation as it exists now, including local
changes, against its documented contracts and pinned FFmpeg behavior.

Do not access `main`, `master`, remote branches, or historical versions of this
repository. Do not fetch, switch branches, compute a merge base, inspect commit
history, or compare branches. Findings do not need to be newly introduced:
report any actionable defect in the current codebase, regardless of its age.

This is a review task: do not fix implementation code, change tests or
contracts, or commit. Save the complete report to `review.md`; this is the
only intentional repository file edit permitted. Preserve existing user
changes. Put temporary reproductions outside the source tree; ordinary build
and test artifacts may be generated by the validation commands.

Cover the whole current codebase, not just MP3 T29a or a set of changed files.
Prioritize high-risk paths and their callers. Do not assume that completed
task labels, passing CI, comments, or reference vectors prove correctness.

Also assess whether this is a well-designed Zig implementation rather than a
mechanical translation of legacy C. A core goal is a smaller, clearer, more
maintainable codebase through strong types, shared algorithms, and purposeful
`comptime` metaprogramming. Preserve FFmpeg's observable behavior while
improving the implementation structure.

2. Group current files by subsystem and build a risk-based coverage plan.

4. Establish a reachable trigger and observable consequence for each suspected

5. Run relevant available checks below. Report exact commands, outcomes,

## Review priorities

### Correctness and FFmpeg fidelity

- MP3 T29a: MPEG audio header parsing and resynchronization, ID3v1/ID3v2,
  Xing/Info/VBRI/LAME metadata, duration and bitrate estimation, gapless
  information, packet boundaries, seeking, and probe scores and ordering.
  MP3 decoding is outside T29a; do not report its absence as a defect.
- Ogg, FLAC, Vorbis, Opus, WAV/RF64/BW64/Wave64, AU, AIFF/AIFF-C, CAF, and
  raw PCM: framing, chunk/page lengths and padding, codec mappings, sample
  counts, channel layouts, metadata, mux/demux interactions, and supported
  round trips.
- Shared behavior: timestamp units and rounding, missing values, duration,
  seeking and state reset, skip-sample side data, end-of-stream handling,
  backpressure, draining, filter scheduling, resampling, and conversion.
- CLI behavior: option validation, unsupported operations rejected before
  output creation, stream copy, pipes and non-seekable inputs, exit status,
  diagnostics, and propagation of late read/write/flush failures.

### Safety, ownership, and robustness

- Overflow or underflow before bounds checks, casts and signedness, shifts,
  size/offset calculations, untrusted allocation sizes, and alignment.
- Out-of-bounds access, stale reader-buffer views, use-after-free, leaks,
  double frees, uninitialized data, and ownership on partial initialization,
  allocation failure, cancellation, and error returns.
- Empty, truncated, malformed, oversized, fragmented, and unknown-length
  input; zero-progress loops; resource exhaustion; documented limits and
  error precedence. Trace safety assumptions in ReleaseFast explicitly.

### Zig APIs, architecture, and performance

- Verify Zig 0.17.0 APIs against installed standard-library sources or minimal
  compiled checks. Do not flag valid current APIs based on older Zig versions.
- Assess explicit allocator/I/O dependencies, borrowed versus owned data,
  error propagation, public API contracts, module boundaries, registries,
  portability, and whether tests are actually included in the build graph.
- Investigate hot-path allocation, avoidable copies, repeated scans, and
  attacker-controlled superlinear work. Support performance findings with a
  concrete cost argument or measurement. Separate optional improvements from
  correctness defects and ignore cosmetic style preferences.

### Modern Zig design, types, and `comptime` metaprogramming

Treat this as a required architectural review, not a cosmetic style check.
FFmpeg is the behavioral reference; its C macros, struct layouts, manual
dispatch, and historical implementation structure do not have to be copied.
Look for concrete ways to express the same behavior more directly in Zig:

- Find duplicated codec/sample-format variants, repetitive parsing or writing
  routines, long dispatch switches, registration lists, option handlers, and
  parallel metadata tables. Identify which differences are static parameters
  and which require distinct algorithms. Propose a shared implementation only
  when the common behavior and ownership contracts are clear.
- Evaluate `comptime` parameters, functions that return types, and generic
  kernels for real static variation such as sample type, byte order, channel
  count, or codec mode. Prefer one readable algorithm specialized for supported
  variants over many manually maintained copies of the same logic.
- Look for typed descriptors that can serve as a single source of truth for
  registries, option metadata, lookup tables, and repetitive dispatch. Assess
  compile-time validation of duplicate names, signatures, dependencies, and
  invariants. Use current Zig 0.17.0 reflection only when it reduces repetition.
- Assess whether enums, tagged unions, explicit state types, and precise error
  sets can replace magic integers, loosely related flags, sentinel values, or
  ambiguous payloads. Favor APIs that prevent invalid combinations and make
  ownership and state transitions clear.
- Identify C-shaped workarounds, unnecessary pointer indirection, manual type
  erasure, and repeated casts that could be simplified with typed Zig APIs.
  Keep wire-format parsing explicit and preserve checked arithmetic.
- Keep runtime input validation at runtime. Do not recommend `comptime`,
  `inline`, reflection, or generated types merely because they are available.
  Consider compile time, generated machine-code size, diagnostic quality, and
  specialization count alongside runtime performance and source size.
- Prefer a small number of understandable abstractions. Do not replace clear
  code with a metaprogramming framework or optimize for line count alone.
  Distinguish duplicated implementation from necessary tables, independent
  scalar oracles, fixtures, provenance, and genuinely different algorithms.

For each worthwhile opportunity, name the repeated code and concrete files,
describe the proposed types and compile-time parameters, and explain what code
would disappear. Include a small illustrative sketch when useful, plus the
behavior-preservation tests and tradeoffs. Treat source-size savings as an
estimate unless measured. Do not claim performance improvements without
evidence or recommend changing documented behavior to simplify the port.

Save the complete report to `review.md`. Start with a 2–4 sentence assessment
of the current codebase, the scope actually reviewed, and the main risks.

   - A short title and the smallest useful `path:line` range in the reviewed

4. **Validation and coverage**, including the current branch, HEAD snapshot ID,
